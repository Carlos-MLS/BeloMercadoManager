# Avaliação ISO/IEC 25010 — Belo Mercado Manager

O modelo de qualidade ISO/IEC 25010 organiza a qualidade de um produto
de software em 8 características principais. Esta avaliação mapeia
cada característica às evidências observáveis no projeto, com nota
qualitativa de 1 a 5.

> Escala: 1 = não tratado · 2 = tratado parcialmente, com lacunas
> graves · 3 = tratado, com algumas lacunas · 4 = bem tratado,
> lacunas menores · 5 = exemplar.

## 1. Functional Suitability (Adequação Funcional)

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Functional Completeness | 4 | 15/19 UCs implementados (UC07, UC08, UC14, UC18 explicitamente fora de âmbito por ADR). Matriz [matriz-srs.md](matriz-srs.md) cobre 100 % dos RFs em âmbito. |
| Functional Correctness  | 4 | 165 testes automatizados a passar. Regras de negócio sensíveis (5 falhas → lockout, anti user-enumeration, diferença caixa > 10 €, retry idempotente) têm testes dedicados. |
| Functional Appropriateness | 4 | UCs mapeiam diretamente ao processo real de uma cadeia de 5 lojas (sales/stock/orders). Sem features superficiais ("dimensões extra"). |

**Resumo:** sólido. Falham apenas RNFs de performance/usabilidade
porque não foram especificados quantitativamente no SRS.

## 2. Performance Efficiency

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Time Behaviour      | 3 | Suite de testes corre em ~3 s (165 testes). Sem testes de carga / SLA documentado. Cada operação POS é uma single-transaction com queries indexadas (índices definidos nas Configurations EF Core). |
| Resource Utilization | 3 | EF Core async + sem N+1 nos repositórios principais (`Include` cuidadoso). Sem profiling de memória. |
| Capacity            | 2 | Sem benchmark de carga; não há testes que validem comportamento sob X transações/min. Para 5 lojas + ~50 vendas/dia, a arquitectura SQL Server tem folga suficiente (ADR-001). |

**Lacuna:** não foram corridos testes de carga. Para o âmbito
académico, aceitável; para produção exigiria k6/Bombardier.

## 3. Compatibility

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Co-existence | 4 | App standalone — não há outros sistemas no mesmo host. Docker isolation para SQL Server. |
| Interoperability | 4 | API REST/JSON com OpenAPI (Swashbuckle). Errors em `application/problem+json` (RFC 7807). Versionada via URL (`/api/v1`). Frontends conhecem apenas a API. |

## 4. Usability

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Appropriateness Recognizability | 3 | UI Blazor com terminologia de domínio (Caixa, Venda, Encomenda). |
| Learnability | 3 | POS desenhado para ≤ 4 toques (WF-01 do relatório). Não testado empiricamente. |
| Operability | 3 | Touch targets ≥ 60×60 px (regra de design). |
| User Error Protection | 4 | Confirmações em operações destrutivas. Erros do servidor em problem+json com `error_code` legível. Diferenças >10 € exigem justificação obrigatória. |
| User Interface Aesthetics | 3 | Estilo consistente; sem branding completo (académico). |
| Accessibility | 2 | Sem auditoria WCAG. Sem alt text formal. |

**Lacuna:** acessibilidade. Recomendação futura: ferramenta como
axe-core num teste de browser.

## 5. Reliability

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Maturity | 4 | 165 testes passam reprodutivelmente. Algoritmos centrais (NIF, EAN-13, BCrypt password policy) cobertos por testes orientados a equivalence partitioning. |
| Availability | 3 | Arquitectura centralizada (1 servidor + 1 SQL) sem alta disponibilidade. ADR-001 documenta o trade-off (académico). |
| Fault Tolerance | 4 | ConsolidationService tem retry (3 tentativas) + estado *Falha* persistido. Idempotency-Key obrigatório em vendas. Refresh tokens rotacionam. Account lockout protege contra brute-force. |
| Recoverability | 3 | Persistência ACID via EF Core transactions. Sem backups automáticos especificados (responsabilidade do operador SQL Server). |

## 6. Security

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Confidentiality | 4 | Passwords com BCrypt (cost 11). Connection string + JWT key apenas em User Secrets. HTTPS assumido em produção. |
| Integrity | 5 | Toda escrita em transação ACID. Audit log imutável por design (sem update path). Idempotency previne escrita duplicada. |
| Non-repudiation | 4 | AuditService regista userId, ação, timestamp, IP, target — para todas as operações de escrita. Testado transversalmente. |
| Accountability | 4 | LogAuditoria queryável por target/ação/utilizador. |
| Authenticity | 5 | JWT assinado HS256. Refresh tokens rotacionam, antigos são invalidados. Lockout após 5 falhas. **Anti user-enumeration** ativo (BCrypt sempre invocado mesmo p/ email inexistente — RN02 UC15) — coberto por teste `Login_EmailDesconhecido_*`. |

**Destaque positivo:** ISO 25010 dá ênfase a *Authenticity*, e o
projecto trata-a com cuidado (timing-safe verify) que muitos sistemas
comerciais descuram.

## 7. Maintainability

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Modularity | 5 | 6 projetos (Domain, Application, Infrastructure, Api, PosWeb, BackofficeWeb) com fronteiras claras. CLAUDE.md documenta regras de project references. |
| Reusability | 4 | DTOs partilhados entre API e Web. Validators stateless (NIF, EAN). |
| Analysability | 4 | Estrutura por feature (Services/, Dtos/, Interfaces/). Constantes (`AuditAcoes`, `*ErrorCodes`) para evitar magic strings. |
| Modifiability | 4 | Mudanças isoladas: alterar regra de promoção toca apenas em `SalesService.CriarVendaAsync` + um teste. |
| Testability | 5 | Interfaces para todas as dependências externas (repos, hasher, token gen, clock, audit). 165 testes em ~3 s. Test doubles reutilizáveis. |

**Destaque positivo:** a injecção do `IClock` (com `FakeClock` em
testes) permite testar regras temporais (lockout, idade de venda)
sem hacks.

## 8. Portability

| Sub-característica | Nota | Evidência |
|--------------------|:----:|-----------|
| Adaptability | 4 | .NET 8 → Linux/Windows/macOS. SQL Server em Docker. Configuração via User Secrets / env vars. |
| Installability | 4 | `setup.txt` + comandos `dotnet run` + Docker compose-like (instruções no CLAUDE.md). |
| Replaceability | 3 | Repositórios via interface — em teoria, mudar p/ PostgreSQL exigia novos repos. EF Core ajuda mas migrations são SQL-Server-specific. |

## Resumo

| Característica         | Nota |
|------------------------|-----:|
| Functional Suitability | **4** |
| Performance Efficiency | **3** |
| Compatibility          | **4** |
| Usability              | **3** |
| Reliability            | **4** |
| **Security**           | **4.5** |
| **Maintainability**    | **4.5** |
| Portability            | **3.5** |
| **Média ponderada**    | **3.8 / 5** |

### Pontos fortes

* **Security**: anti user-enumeration, BCrypt timing-safe, lockout,
  refresh token rotation, audit log universal.
* **Maintainability**: modularidade + testabilidade ≥ 4.5; permite à
  equipa iterar com confiança.
* **Functional Correctness**: 165 testes a passar com regras de
  negócio explicitamente verificadas.

### Pontos a melhorar

* **Performance**: faltam testes de carga e profiling.
* **Usability/Accessibility**: nenhuma auditoria automatizada de WCAG.
* **Reportability**: o `ReportingService` ainda não tem testes
  unitários dedicados.

### Plano de melhoria sugerido (priorizado)

1. Adicionar uns testes de smoke para o `ReportingService` com a
   fixture de integração.
2. Cobrir UC10 `AtualizarEncomendaRascunhoAsync` e `CancelarEncomendaAsync`.
3. Configurar GitHub Actions para correr a suite e impor coverage ≥ 70 %.
4. Adicionar k6 ou Bombardier num smoke load para o endpoint POST /vendas
   (alvo: 200 req/min sustentado por 1 min).
